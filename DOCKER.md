# Запуск проекта в Docker — инструкция

Весь проект (MySQL + backend + frontend) запускается одной командой:

```
docker compose up --build
```

Ниже: что нужно установить, как запустить, как всё это устроено и что делать, если что-то пошло не так.
Раздел «Как это устроено» написан для того, чтобы вы могли разобраться в Docker сами, а не просто нажать кнопку.

---

## 1. Что получится

```
 Браузер ──► frontend (nginx, порт 5173) ──/api/──► backend (FastAPI, порт 8000) ──► db (MySQL)
                  │                                      │                              │
          отдаёт React-сайт                       бизнес-логика                  данные в томе db_data
```

Три контейнера, которые видят друг друга по именам сервисов (`db`, `backend`, `frontend`) внутри сети, которую Docker Compose создаёт сам.

---

## 2. Подготовка (один раз)

1. Установите **Docker Desktop** для Windows: https://www.docker.com/products/docker-desktop/
2. При установке оставьте включённым **WSL 2** (на Windows 10/11 это вариант по умолчанию). Если Docker Desktop пожалуется на виртуализацию, её нужно включить в BIOS (Intel VT-x / AMD-V).
3. Запустите Docker Desktop и дождитесь, пока в левом нижнем углу будет зелёный статус *Engine running*.
4. Проверьте в PowerShell:
   ```
   docker --version
   docker compose version
   ```
   Обе команды должны вывести версию. Если `docker` не найден, перезапустите PowerShell или компьютер.

Остановите локальный запуск проекта (uvicorn и `npm run dev`), чтобы не занимать те же порты 8000 и 5173.

---

## 3. Первый запуск

1. Откройте PowerShell **в папке проекта** — там, где лежит `docker-compose.yml`:
   ```
   cd C:\Users\Arkady\Downloads\fullstack-project
   ```
2. Выполните:
   ```
   docker compose up --build
   ```
3. Первый раз будет долго (несколько минут): Docker скачивает образы MySQL, Python, Node, nginx и собирает проект. Дальше запуск занимает секунды.
4. Готово, когда в логах появится строка про то, что база данных готова, а затем `Application startup complete`. Не закрывайте окно: если нажать `Ctrl+C`, контейнеры остановятся. Чтобы работать в фоне, запускайте с `-d` (см. раздел 5).

**Адреса:**

| Что | Адрес |
|---|---|
| Сайт | http://localhost:5173 |
| API + Swagger (документация) | http://localhost:8000/docs |
| MySQL для Workbench | `127.0.0.1`, порт **3307**, пользователь `root`, пароль `12345` |

**Вход на сайт.** Если вы запускаете проект с пустой БД, при первом старте автоматически создаются:

| Роль | Логин | Пароль |
|---|---|---|
| Администратор | `admin` | `admin` |
| Сотрудник (демо) | `ivan` | `ivan` |

Эти записи появляются **только в совсем пустой базе**. Если вы используете свою БД с готовыми сотрудниками, ролями и паролями (раздел 6), скрипт ничего не добавляет и вы входите под своими логинами. Демо-данные можно отключить через `SEED_DEMO_DATA=false` (раздел 7).

---|---|---|
| Администратор | `admin` | `admin` |
| Сотрудник (демо) | `ivan` | `ivan` |

Демо-сотрудник и несколько СИЗ добавляются только в пустую базу. Отключить можно через `SEED_DEMO_DATA=false` (раздел 7).

## 4. Как это устроено (разбор файлов)

### Основные понятия

- **Образ (image)**: «заготовка» с программой и всем окружением. Собирается по `Dockerfile`.
- **Контейнер**: запущенный экземпляр образа. Его можно удалить и создать заново, ничего не потеряв, если данные лежат в томе.
- **Том (volume)**: папка, которой управляет Docker. Здесь он хранит файлы MySQL, поэтому данные не пропадают при перезапуске.
- **Слой**: каждая инструкция в `Dockerfile` создаёт слой, и Docker кэширует их. Поэтому в `backend/Dockerfile` сначала копируется `requirements.txt`, а потом код: при правке кода зависимости заново не ставятся.
- **Docker Compose**: описывает в одном файле сразу несколько контейнеров и их связи.

### `docker-compose.yml`: главный файл
Описывает три сервиса.

- **`db`** берёт готовый образ `mysql:8.0` и при первом запуске создаёт базу с именем из `MYSQL_DATABASE`. `volumes: db_data` сохраняет данные. `healthcheck` каждые 5 секунд проверяет, что MySQL отвечает.
- **`backend`** собирается из папки `backend/` (`build: ./backend`). `DB_HOST: db` означает, что БД ищется по имени сервиса. `depends_on` с `service_healthy` заставляет ждать готовности MySQL.
- **`frontend`** собирается из папки `frontend/`. Порт `5173:80` означает: *порт компьютера : порт внутри контейнера*.
- Запись `${DB_PASSWORD:-12345}` читается как «возьми переменную `DB_PASSWORD` из файла `.env`, а если её нет, то `12345`». Поэтому проект работает и без `.env`.

### `backend/Dockerfile`
1. `FROM python:3.12-slim` — основа: Linux с Python.
2. Ставит `tzdata`, чтобы работала переменная `TZ` (часовой пояс влияет на то, какая дата считается «сегодня» при подсчёте просрочек).
3. Копирует `requirements.txt` и ставит зависимости, затем копирует код.
4. Запускает сервер не от root (`USER appuser`).
5. `CMD` сначала выполняет `python -m app.init_db`, а потом запускает `uvicorn`.

### `backend/app/init_db.py`: подготовка БД
В новой MySQL ничего нет, поэтому скрипт при каждом старте:
1. ждёт, пока БД ответит;
2. создаёт недостающие таблицы (существующие и данные не трогает);
3. добавляет статусы «Выдано» и «Сдано», если их нет (без них не работают выдача и сдача СИЗ);
4. **только если в БД нет ни одного сотрудника**: создаёт администратора и (при `SEED_DEMO_DATA=true`) демо-данные.

Если сотрудники уже есть (например, вы импортировали свою базу), пункт 4 пропускается: ваши пользователи и пароли остаются как есть, лишних учёток не добавляется. Скрипт идемпотентный: повторный запуск ничего не дублирует.

### `frontend/Dockerfile`: сборка в два этапа
- **Этап 1** (`node:20-alpine`) ставит зависимости (`npm ci`) и собирает сайт (`npm run build`) в обычные статические файлы.
- **Этап 2** (`nginx:alpine`) берёт из первого этапа только готовую папку `dist`. Node в итоговый образ не попадает, поэтому он маленький.

### `frontend/nginx.conf`
- Файлы сайта отдаются как есть, а неизвестные пути возвращают `index.html` (так работают одностраничные приложения).
- Запросы на `/api/...` пересылаются на `http://backend:8000`. Браузер видит один адрес, поэтому CORS не нужен. Это то же самое, что делает `proxy` в `vite.config.js` при локальной разработке.

### `.dockerignore`
Список файлов, которые не отправляются в сборку: `node_modules`, `.venv`, `.env`. Это ускоряет сборку и не даёт случайно положить пароли в образ.

### `.env.example`
Шаблон настроек. **Это не `backend/.env`**: тот нужен только при запуске без Docker, а в контейнер он не попадает.

## 5. Повседневные команды

Выполняются в папке с `docker-compose.yml`.

| Что нужно | Команда |
|---|---|
| Запустить в фоне (пересобрать, если код менялся) | `docker compose up --build -d` |
| Запустить с выводом логов в окно | `docker compose up` |
| Посмотреть, что запущено | `docker compose ps` |
| Логи всех сервисов (следить в реальном времени) | `docker compose logs -f` |
| Логи только backend | `docker compose logs -f backend` |
| Остановить (данные сохранятся) | `docker compose down` |
| Остановить и **удалить данные БД** | `docker compose down -v` |
| Перезапустить один сервис | `docker compose restart backend` |
| Пересобрать один сервис после правок | `docker compose up --build -d backend` |
| Зайти внутрь контейнера | `docker compose exec backend sh` |
| Открыть консоль MySQL | `docker compose exec db mysql -uroot -p12345 siz_system` |
| Заново подготовить БД вручную | `docker compose exec backend python -m app.init_db` |
| Сколько места занимает Docker | `docker system df` |

**После правки кода** (Python, React) нужно пересобрать образ: `docker compose up --build -d`. Контейнер работает с копией кода, которая была на момент сборки. Для быстрой разработки удобнее по-прежнему запускать проект локально (`uvicorn --reload` и `npm run dev`), а Docker использовать для проверки «как в готовом виде».

## 6. Данные и перенос вашей БД

**Важно:** база в Docker **отдельная** от MySQL, который стоит у вас на компьютере. Данные из локальной базы там автоматически не появятся, их нужно перенести один раз.

Чем отличаются остановки:
- `docker compose down` удаляет контейнеры, но **том с данными остаётся**.
- `docker compose down -v` удаляет **и данные** (полный сброс, при следующем запуске БД создастся заново).

### Как использовать свою БД (сотрудники, роли, логины и пароли из неё)

Порядок важен: сначала загружаем данные, и только потом запускаем backend.

1. **Экспорт.** В MySQL Workbench: *Server → Data Export*, выберите свою базу, режим *Export to Self-Contained File* (например `dump.sql` в папку проекта), отметьте *Dump Structure and Data*.
2. **Настройки.** Скопируйте шаблон `copy .env.example .env` и в `.env` впишите **настоящее имя вашей базы**:
   ```
   DB_NAME=имя_вашей_базы
   ```
   Это имя должно совпадать с тем, что в дампе (`CREATE DATABASE` / `USE`), если они там есть.
3. **Чистый старт** (если вы уже запускали проект раньше):
   ```
   docker compose down -v
   ```
4. **Поднимите только базу** и дождитесь статуса `healthy`:
   ```
   docker compose up -d db
   docker compose ps
   ```
5. **Загрузите дамп** (PowerShell, в папке проекта; `ИМЯ_БАЗЫ` замените на своё):
   ```
   docker compose cp dump.sql db:/tmp/dump.sql
   docker compose exec db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ИМЯ_БАЗЫ < /tmp/dump.sql'
   ```
   Ошибка `Unknown database` значит, что `DB_NAME` в `.env` отличается от имени базы.
6. **Запустите остальное:**
   ```
   docker compose up --build -d
   ```
7. Заходите на http://localhost:5173 **под своими логинами и паролями**. Демо-пользователи не создаются, потому что в базе уже есть сотрудники.

Проверить, что данные на месте:
```
docker compose exec db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ИМЯ_БАЗЫ -e "SELECT ID_Employee, Login, Role FROM employee;"'
```
(Если у вашей таблицы другое имя, замените `employee`.)

### Резервная копия данных из Docker
```
docker compose exec db sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" ИМЯ_БАЗЫ' > backup.sql
```

## 7. Настройки (`.env`)

1. Скопируйте шаблон: `copy .env.example .env`
2. Отредактируйте нужные значения и перезапустите: `docker compose up -d`

Что имеет смысл поменять сразу:

| Переменная | Зачем |
|---|---|
| `TZ` | Ваш часовой пояс (например `Europe/Moscow`), иначе «сегодня» считается по UTC |
| `SECRET_KEY` | Ключ подписи токенов. Поставьте длинную случайную строку |
| `ADMIN_PASSWORD` | Пароль администратора. Применяется только если БД совсем пустая (со своей БД не используется) |
| `DB_NAME` | Имя вашей базы, если переносите свою БД (раздел 6) |
| `SEED_DEMO_DATA` | `false`, если демо-данные не нужны (в заполненной БД они и так не добавляются) |
| `FRONTEND_PORT`, `BACKEND_PORT`, `DB_HOST_PORT` | Если порт занят другой программой |

**Ловушка:** пароль БД (`DB_PASSWORD`) и имя базы применяются только при **первом создании** тома. Если поменять их позже, будет ошибка `Access denied`. Нужно либо вернуть старое значение, либо сбросить данные: `docker compose down -v`, а потом запустить заново.

## 9. Если что-то не работает

| Симптом | Что делать |
|---|---|
| `error during connect` / `cannot connect to the Docker daemon` | Docker Desktop не запущен. Откройте его и дождитесь *Engine running* |
| `no configuration file provided: not found` | Вы не в той папке. Перейдите туда, где лежит `docker-compose.yml` |
| `port is already allocated` / `address already in use` | Порт занят (часто 8000 или 5173: остался локальный запуск). Остановите его или поменяйте порт в `.env` |
| Сайт открывается, но входа нет, ошибка 502 | backend ещё стартует. Подождите 20–40 секунд, смотрите `docker compose logs -f backend` |
| backend `unhealthy` или всё время перезапускается | `docker compose logs backend`: там будет причина (чаще всего подключение к БД) |
| `Access denied for user 'root'` | Пароль БД изменён после первого запуска (см. ловушку в разделе 7) |
| `Unknown database` | Имя базы изменено после первого запуска. То же решение: `docker compose down -v` |
| Правки кода не видны | Нужна пересборка: `docker compose up --build -d`. Обновите страницу с `Ctrl+F5` |
| Хочу начать с нуля | `docker compose down -v`, затем `docker compose up --build` |
| Закончилось место на диске | `docker system prune` удаляет неиспользуемые образы и кэш (запущенные контейнеры и тома не трогает) |

Если ничего не помогло, выполните `docker compose logs > logs.txt` и пришлите содержимое файла: по нему обычно сразу видно причину.

## 10. Перед использованием «по-настоящему»

Текущие настройки подходят для обучения и локальной работы. Для реального использования:
- смените `SECRET_KEY`, `DB_PASSWORD` и пароль администратора;
- уберите публикацию порта MySQL (строку с `DB_HOST_PORT` в `docker-compose.yml`), если не нужен доступ из Workbench;
- смените слабые пароли (`admin`/`admin`, `1`/`1` и подобные): хэширование защищает от утечки базы, но не делает слабый пароль сильным (см. раздел 12).

## 12. Пароли, хэши и токены входа

**Пароли** в БД хранятся не открытым текстом, а как **bcrypt-хэш**: строка из 60 символов вида `$2b$12$...`. Хэш необратим, исходный пароль из него восстановить нельзя, а у каждого пользователя своя «соль». Поэтому, даже если кто-то получит копию базы, пароли из неё он не прочитает.

**Логины не хэшируются.** Логин не секрет, а идентификатор: администратор ищет сотрудника по логину и видит его в карточке. Хэш логина сломал бы поиск и отображение, а защиты не добавил бы.

### Что произойдёт с вашими существующими учётками
Пароли `admin` / `1` в БД лежат открытым текстом. Они переведутся в хэши автоматически, **сами пароли для входа не меняются**:
- при запуске backend в Docker (скрипт `init_db` переводит все такие записи разом);
- и/или при первом успешном входе пользователя (если запускаете без Docker).

Посмотреть результат:
```
docker compose exec db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ИМЯ_БАЗЫ -e "SELECT Login, LEFT(Password, 7) FROM employee;"'
```
У всех пользователей в столбце должно быть `$2b$12$`.

### Смена пароля и новые пользователи
Хэш нельзя редактировать вручную, поэтому пароль меняется командой (ввод скрыт, пароль сохраняется хэшем):
```
docker compose exec backend python -m app.set_password admin
```
Без Docker: `python -m app.set_password admin` из папки `backend`.

Нового пользователя можно добавить в Workbench с обычным паролем: при следующем запуске backend или при первом входе он автоматически станет хэшем (до этого момента он лежит в базе открытым текстом, поэтому не оставляйте так надолго).

### Хэширование делается один раз
Пароль превращается в хэш **однократно**: при запуске backend в Docker или при первом успешном входе. После этого хэши автоматически не пересоздаются и не обновляются. Токены входа подписываются обычным `SECRET_KEY` и живут 8 часов. Настройка `BCRYPT_ROUNDS` влияет только на хэши, которые создаются заново (новые пользователи, смена пароля, первое хэширование).

### Если пароль не сохраняется в виде хэша
Столбец `employee.Password` должен вмещать 60 символов (в Docker `init_db` расширит его сам). При запуске без Docker проверьте и при необходимости расширьте вручную:
```sql
DESCRIBE employee;
ALTER TABLE employee MODIFY Password VARCHAR(255) NOT NULL;
```
Если столбец короткий, вход продолжит работать, а в логах backend будет предупреждение «Не удалось сохранить хэш пароля».
